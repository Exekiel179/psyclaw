# PsyClaw 开发进展：从“能做”到“做得稳”

**日期:** 2026-08-05

**版本基线:** `psyclaw 0.22.0`

## 先说判断

PsyClaw 已经不是一个把统计命令重新包一遍的工具。

它现在更像研究工作的交通系统：负责把问题送到合适的流程，把统计交给成熟工具，把文献和产物留下来，再在交付前拦住明显的错误。

这条路线是对的，但“路线对”不等于“产品完成”。

真正影响使用感的，已经从“有没有能力”转向三个更朴素的问题：生成的 Word 是否稳定，几个入口是否容易理解，外部开源能力能否真正接上而不是只停在目录里。

机器可读台账显示，`feature_list.json` 有 175 个 feature，当前全部为 `done`。这说明已有计划基本收官，不说明所有真实工作流都已经打磨完成。

另外，`dev/session-handoff.md` 仍记录着 `v0.15.0` 的旧交接状态。它应该尽快更新，否则项目会出现“代码已经往前走，文档还留在原地”的双重现实。

## 已经站稳的部分

### 研究流程

`chat / run / auto` 三个入口已经形成基本骨架。`run` 负责按步骤执行，`auto` 负责感知项目状态并推动下一步，`chat` 负责日常协作和临时决策。

Workflow 引擎已经有前置检查、人工确认、恢复检查点、产物记录和总验收。统计计算则交给外部库或 MCP，仓库不再重复实现 scipy、pingouin 一类的算法。

这是一条重要的边界：PsyClaw 不负责成为又一个统计软件，而负责让统计软件在正确的研究流程里被使用。

### 文献和证据

文献链条已经比较完整：多源检索、检索计划、结果导入、文献矩阵、引用滚雪球、全文下载和引用核查都已有对应入口。

公开来源、机构权限和浏览器桥接有不同的降级路径。遇到付费墙时会承认拿不到，而不是把摘要或网页简介伪装成全文。

`cite` 现在同时承担两件事：生成 APA7 参考文献，以及检查正文引用和参考文献表是否相互对应。这个方向比维护一份静态“权威背书库”可靠得多。

PDF 下载也已有 `%PDF` 文件头检查、规范命名和来源状态记录。但文件哈希、重复文件治理和 Zotero 的端到端交接还没有完全闭合。

### Skill、记忆和质量控制

内置 Skill、外部 Skill、目标期刊包都可以被发现、推荐和安装。三层记忆、事实卡、教训卡、睡眠整合和会话恢复，也已经形成了可运行的基础设施。

失败经验不会直接变成“永久真理”，而是先进入候选层，再通过复现或回归测试。这条规则值得保留，因为错误经验也会学习，而且通常学得很快。

gates、JARS、provenance、cite-check、效应量与置信区间、探索性和确证性区分，已经进入执行链。统计脚本没有真正运行时，不会给出带具体数字的“示例结果”。

### 交互和交付

REPL 已经具备 `prompt_toolkit`、命令补全、状态栏、审批模式、流式输出、图片内联和独立研究目录。

APA7、心理学报、心理科学等 Word 导出格式也已有实现。问题不在“能不能导出”，而在“同一份输入能不能每次都导出得差不多”。这正是下一阶段要解决的交付问题。

## 分享资料能复用什么

分享资料里最值得借鉴的，不是项目名单，而是它们对“中间层”和“证据边界”的重视。

| 资料中的路线 | PsyClaw 现在的情况 | 下一步判断 |
|---|---|---|
| MarkItDown：异构材料统一为 Markdown | 已有材料读取和 Markdown 产物，但没有统一的全格式转换层 | 应优先接入，而不是让每个流程各写一套解析器 |
| Session Handoff：跨会话接力 | 已有交接文件、SQLite 会话、状态和 `resume` | 能力已有，先修文档版本滞后问题 |
| Paper Search MCP：多源检索和 OA 回退 | `lit` 已有多源、滚雪球、机构库桥接和下载 | 继续做真实来源回归，不急着再加来源 |
| ScholarBridge：PDF 质控、哈希、审计、Zotero | 已有 PDF 校验、命名、来源记录和 Zotero 联动 | 补 SHA-256、去重和可重放交接包 |
| Academic Reference Matcher：Claim-Evidence | cite-check 和 provenance 已有相近能力 | 统一 `claim` 数据结构，减少重复账本 |
| Corpus2Skill / OpenKB：资料编译成知识结构 | 已有 Skill loader 和外部 Skill 安装 | 缺一个“资料→索引→可导航 Skill”的编译流程 |
| OmniDistill：证据驱动的 Skill 蒸馏 | 已有记忆、教训卡和回归评测 | 可借其分层和晋升规则，但不照搬整套产品 |
| pskoett：从失败中持续改进 | 错误自学习、教训卡和睡眠整合已落地 | 补候选、晋升、回滚的治理记录 |
| CodePivot：桌面 Agent 工作台 | 当前仍是本地 CLI/REPL | 暂不自建桌面壳，先把 CLI 交付做稳 |
| SmartPlot：科研绘图和 MCP | 有图片渲染和图形能力提示，不是完整绘图平台 | 通过 MCP 接入，不在本体重造绘图引擎 |

一句话概括：先借协议，再借实现；先接能复用的部分，再决定是否长期维护。

## 下一阶段开发代办

### 1. Word 导出稳定性：从“能生成”到“可验收”

目前 Word 导出最现实的问题是格式漂移：同样的生成指令，有时标题、粗体、表格、摘要、参考文献或分页并不稳定。

这不是排版小问题。对研究者来说，格式不稳就意味着无法放心交付，也无法判断一次修改到底改了内容还是改了样式。

计划：

1. 建立固定的 Word fixture，覆盖标题层级、粗斜体、表格、脚注、参考文献、分页和中文字符。
2. 导出后重新读取 DOCX，检查段落样式、文字 runs、表格结构和关键文本是否符合契约。
3. 把“生成指令”拆成可检查的版式契约，而不是只把自然语言提示交给模型。
4. 增加 DOCX→PDF/图片的渲染回归，比较关键页面的结构和视觉差异。
5. 对不符合契约的产物明确标记为失败，保留中间文件和诊断信息，不静默交付。

验收标准：同一 fixture 在连续运行中保持稳定；失败时能指出是内容、样式还是分页不符合要求；真实论文样稿通过人工抽查。

金句：Word 导出不是“最后按一下按钮”，而是研究结果的最后一个实验环节。

### 2. 心智地图统一：重新划清 `chat`、`run`、`auto`

目前三个入口有功能重叠。用户可以在 `chat` 里让模型调用工具，也可以在 `run` 里跑流程，还可以让 `auto` 感知待办后继续推进。

实现层的复用是优点，产品层的边界模糊就是成本。用户不应该为了找到入口，先理解内部的 router、workflow 和 loop。

建议固定成三句话：

- `chat`：我和你一起做，过程中可以随时改变方向。
- `run`：按已经确定的步骤做完一项研究任务。
- `auto`：根据项目状态自己找下一步，但在关键节点停下来问人。

需要同步修改启动提示、README、教程、命令补全、状态栏和新建项目 README，并为三种入口各写一个最小真实案例。

验收标准：新用户只看启动界面和项目 README，就能判断该用哪个入口；同一任务在三个入口之间切换时，目标、产物和状态不丢失；不再出现三个入口各自维护一套近似执行逻辑。

洞见：心智模型不是文档装饰，它决定用户把错误归因给自己，还是归因给产品。

### 3. 开源框架复用：从“列出来”到“接起来”

分享资料里的开源项目可以分成三类：可以直接作为依赖的工具，可以借鉴数据协议的框架，以及只适合参考边界的产品。

计划先做一张复用清单，逐项写明许可证、维护状态、接口稳定性、引入成本、替代方案和退出路径。没有退出路径的依赖，实际上不是复用，而是押注。

优先级建议：

1. 用 MarkItDown 类方案补资料转换中间层。
2. 参考 ScholarBridge 补 PDF 哈希、来源审计和 Zotero 交接。
3. 参考 Academic Reference Matcher 和 OmniDistill，统一 Claim-Evidence 及 Skill 蒸馏记录。
4. 参考 CodePivot 的受控桥接思路，但暂不启动桌面 UI 项目。
5. 通过 MCP 接入 SmartPlot 或其他成熟绘图工具，不在 PsyClaw 内复制绘图引擎。

金句：开源框架最有价值的地方，往往不是它的代码，而是它已经替你踩过的坑。

## 有意跳出框架的几个判断

第一，PsyClaw 不一定要变成一个“全自动科研 Agent”。在很多研究环节，最好的产品不是替用户做决定，而是让决定留下证据、让错误尽早暴露。

第二，Word 稳定性可能比再增加一个检索源更值得投入。研究者通常可以容忍少找一个来源，却很难接受交付稿件每次打开都不一样。

第三，Skill 越多不代表能力越强。真正稀缺的是能够判断“现在不该调用什么”的机制，包括停止、转人工、保留不确定性和拒绝编造。

第四，可以考虑把“研究产物”作为第一等对象，而不是把命令作为第一等对象。

命令只是入口，真正需要管理的是检索计划、文献矩阵、数据画像、统计结果、稿件和审查记录之间的关系。

## Agent 评估：不只看回答像不像人

目前已有离线 eval 和大量单元测试，但评估重点仍偏向工具循环、门禁和命令契约。下一阶段需要把 Agent 当成一个会选择路径、调用工具、写文件并接受纠错的系统来测。

评估至少分为六个面：

- **路由正确性**：面对同一个研究目标，能否选对 `chat`、`run` 或 `auto`，并在需要时停下来澄清。
- **执行可靠性**：工具参数错误、网络失败、依赖缺失、输出截断时，能否重试、降级或如实停止。
- **事实与证据纪律**：不编造文献、不编造统计结果，能把结论和来源、脚本、审查记录对应起来。
- **产物质量**：生成的文献矩阵、分析脚本、稿件和 Word 是否符合结构契约，而不只是回复文本看起来完整。
- **安全与边界**：涉及写盘、联网、机构库和原始数据时，是否遵守审批、沙箱和权限边界。
- **纠错与恢复**：用户纠正后是否真正改变后续行为，跨会话恢复时是否保留目标、产物和未完成步骤。

测试不应只用“最终答案对不对”一个分数。建议同时记录任务完成率、关键工具调用成功率、无依据断言数、人工介入次数、恢复成功率、产物可重放率和回归失败数。

测试集采用四层结构：确定性单测验证纯函数；离线 harness eval 验证工具循环和门禁；沙盒场景测试验证从输入到文件产物的闭环；最后用真实研究任务做人工抽查。

三条新代办都应进入评估集：Word 样稿检查格式漂移，入口选择题检查心智模型，开源框架接入题检查是否真的调用外部能力而不是只给安装建议。

每个评估用例都要保存输入、工具轨迹、文件差异、最终产物和判定理由。只保存模型最后一段话，无法解释它为什么成功，也无法修复它为什么失败。

评估门槛建议采用“硬失败优先”：编造引用、伪造数值、越权写盘、破坏原始数据、绕过审批，任一出现即判失败；格式瑕疵和措辞问题再单独计分。

金句：一个 Agent 的能力，不在于它能说出多少，而在于它知道什么时候不能继续说。

## 暂不做什么

- 不直接复制 PDF 中的第三方项目，不把项目名堆成新的依赖清单。
- 不在仓内重写 scipy、pingouin、statsmodels、SPSS、Mplus、Stata 或 SmartPlot 的核心算法。
- 不绕过机构认证、验证码、付费墙，也不保存用户账号密码。
- 不把人物或导师蒸馏结果写成“本人真实想法”，必须区分证据、推断和未知。
- 不把“175 个 feature 全部 done”误读成“所有真实场景都已验证”。

## 当前验证口径

- `python3 -m psyclaw version` → `psyclaw 0.22.0`。
- `dev/feature_list.json` → 175 个 feature，全部为 `done`。
- 本次只修改本进展文档，没有修改产品代码，也没有回滚工作区已有变更。
- 新增能力进入开发前，应重新运行全量测试、`gates` 和 `eval`，并补真实长文档、机构库和 Word 样稿验证。

## 收束

下一阶段不是继续证明 PsyClaw “什么都能做”，而是把几个关键动作做得可重复、可检查、可交接。

资料转换要有中间层，文献获取要有审计，Skill 蒸馏要有证据，Word 导出要有验收，入口设计要让人一眼明白。

如果这些事情做稳，PsyClaw 才会从一个功能丰富的研究工具，变成一个值得长期托付研究工作的基础设施。
