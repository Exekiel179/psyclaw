## 0. 背景

复现测评（37 号论文，2026-10）中发现两件事：

1. **agent 从不读 core skill 正文。** v6 的 6 次无头运行里，读取 `skills/core/analysis-plan/SKILL.md` 的次数都是 0。模型实际遵循的是 analysis 模式提示，以及 `analysis/plans/plan.md` 模板里的表头和那几行规则。SKILL.md 里写的方法规则（比如"子组假设要用合并模型检验 × group"）因此没有生效。
2. **丢分集中在方法规则上，而不是算错。** 主要是分组拟合代替合并交互模型，以及没有先检验总体变化。每次运行平均约丢 8.5 分，满分 32。

结论：要让规则可靠生效，不能指望模型自己决定去读 skill；同时用户也会带来自己的 skill，需要定好兼容规则。

## 2. 目标

1. **方法规则可靠生效**，不依赖模型自己决定去读 skill。
2. **按需加载**：篇幅长、只在特定场景才用的细则不常驻提示，以控制 token。
3. **用户 skill 不被吞掉**：用户自带的方法规范能加载，冲突时有确定的优先级，无头模式下也一样。
4. **行为可审计**：每次运行能看出加载了哪些 skill、注入了哪些、谁覆盖了谁。

## 3. 开发项

### A. 方法规则分层，并由代码注入

1. **常驻层**：保持短规则（每条 1–2 句，总量控制在约 300 token 以内），放在 plan 模板和 analysis 模式提示里。现有内容：
   - 子组假设要在合并模型里检验 × group，并报告各组斜率；
   - 有组别因素的调节要检验三阶项；
   - 探索变量既检验主效应，也检验它对各个焦点暴露的调节；
   - 每个结局变量都执行全部隐含检验；
   - 先检验总体变化，再逐步加项；
   - 每个结局变量建一个合并模型，连续变量中心化。
2. **细则层**：拆成 core 方法 skill，一个主题一个，例如：
   - `method-change-scores`：差分分数与 ANCOVA 的取舍、Lord 悖论、先做总体变化检验；
   - `method-interactions`：中心化、简单斜率、Johnson-Neyman、"一组显著、另一组不显著 ≠ 两组有差异"（Gelman & Stern, 2006；Nieuwenhuis et al., 2011）；
   - `method-mediation`、`method-multilevel`、`method-sem`；
   - `report-checklist`：报告前的自查清单，参照 APA JARS-Quant 改写，不照抄原文，因为表格版权归 APA。
3. **注入方式**：扩展 `stats-router`，让 `resolveStatsIntent` 返回识别出的方法主题（可以多个），而不只是 `stats-analysis`。软路由接管时，由代码读取对应 skill 的正文，作为本回合的上下文注入，而不是只写一句"follow the skill"。
   - 每回合注入的总量要设上限（建议 4k token），超出时只注入目录和路径。
   - 同一会话里已经注入过的 skill 不要重复注入。要和 `observation-mask.ts` 的稳定前缀策略配合，注入内容放在不会被裁剪的位置。
   - `report-checklist` 在模型准备写报告时注入。触发点可以选写入 `results/report.md` 或 `paper/` 之前，也可以选进入 handoff 阶段时。
4. **analysis-plan 的 description**：现在写的是流程（人工选择、仪式审批），看不出里面有方法规则。改写 description，或者把方法内容挪到上面的方法 skill 里。

### B. 用户 skill 兼容

1. **同名冲突（已定，2026-10-26）**：
   - **核心 skill 一律不能被覆盖**，方法类和流程类都一样。不需要 `overridable` 字段。
   - 同名的用户 skill 或推荐 skill 照旧跳过，但要**明确提醒**：
     - 交互模式：会话开始时 `ctx.ui.notify` 一条 warning，说明哪个 skill（含路径）因与核心同名被跳过，并建议改名；
     - 无头模式：没有界面，写进 B5 的 resolution 记录，并在 `psyclaw run` 的 receipt 里列出；
     - `/skill` 列表里照旧显示。
   - 用户改名之后，就按第 2 条的"主题冲突"规则处理。
2. **主题冲突（不同名，但和核心方法细则讲同一主题）**：
   - 判定：用户 skill 的 frontmatter `topics` 字段，或 description 关键词，和 A3 识别出的方法主题匹配。
   - **默认以用户 skill 为准**：注入用户 skill 正文，核心细则只附目录、路径和一句"项目中有用户 skill `<name>`（`<path>`），本回合以它为准"。同样受注入总量上限约束。
   - **交互模式让用户选**：第一次在会话里遇到某个冲突时，弹一张选择卡（`ctx.ui.select`），选项：
     1. 用用户 skill（默认，排第一）；
     2. 用核心细则；
     3. 两者都注入（冲突处以用户 skill 为准）。
     - 卡片设超时（建议 60 秒），超时按默认处理；
     - 选择按"冲突对"（核心主题 × 用户 skill 名）记在项目里（例如 `.psyclaw/skill-preferences.json`），以后不再问；提供一个命令或 `/skill` 子命令可以改回或重置。
   - 无头模式不弹卡，读已保存的选择，没有就用默认（用户 skill），并写进 resolution 记录。
   - 注意：A3 注入的核心细则仍算核心 skill，但用户选择的只是"本主题注入哪份正文"，不改变核心 skill 本身，也不影响流程类核心 skill（审批、审核门）的执行。
3. **软路由不要误伤**：`resolveStatsIntent` 遇到下面两种情况时，跳过接管或改为合并接管：
   - 用户消息里出现了某个已加载用户 skill 的名称；
   - 用户消息里有 `/skill:` 前缀。现在 `EXPLICIT_SKIP` 已经处理了这种情况，加测试固定下来。
4. **无头模式**：
   - 没有交互界面，不能弹卡片让用户选，所以完全按第 1、2 条的确定性规则执行：同名冲突跳过并记录，主题冲突按已保存的选择，没有就用用户 skill。
   - 把 `unattendedAnalysisPrompt` 里 "do not explore the PsyClaw scaffolding (.psyclaw/, …)" 改得更窄，只指 plan 和 HANDOFF 模板，并明确"系统提示中列出的 skill 可以读取"。
5. **可审计**：
   - 每次运行在会话里写一条 custom entry（例如 `psyclaw-skill-resolution`），记录加载了哪些 skill（来源：core / recommended / local）、哪些被覆盖或跳过及原因、每回合注入了哪些正文。
   - `psyclaw run` 的 receipt 里带上这份摘要。
   - 现在的 warnings 只在 `/skill` 里可见，无头模式下看不到。

## 4. 验收

- 单元测试：
  - `stats-router` 的主题识别；
  - 注入总量上限与去重；
  - 同名冲突：核心永远胜出，且产生提醒（交互 notify、无头 resolution 记录）；
  - 主题冲突：默认用户 skill；保存的选择生效；卡片超时走默认；重置后重新询问；
  - 软路由在提到用户 skill 时会跳过接管。
- 契约测试（`tests/contract/pi-extension.test.ts`）：
  - 无头（`hasUI=false`）和交互两种情况下，用户 skill 都会出现在 `resources_discover` 的结果里；
  - 无头时 resolution 记录会写入会话。
- 端到端：在一个临时项目的 `.psyclaw/skills/` 和 `.claude/skills/` 下各放一个方法 skill，其中一个和核心方法 skill 同名，然后用 `psyclaw run`（无头）跑一个统计请求，确认：
  1. 用户 skill 被加载；
  2. 和核心同名的那个被跳过，receipt 和 resolution 记录里有提醒；
  3. 另放一个不同名但主题冲突的用户 skill，无头运行时注入的是它的正文；
  4. 会话的 resolution 记录正确；
  5. 软路由没有吞掉用户显式指定的 skill。
- 交互冒烟：在 TUI 里触发一次主题冲突，确认选择卡出现、默认项是用户 skill、选择被保存、第二次不再询问。
- 效果回归：开发完成后，交给测评侧在 37 和 33 号论文上跑一轮（干净容器，不放用户 skill），确认分数不下降、token 不明显上升。这一步由测评侧负责，不阻塞开发合入。

## 5. 不做的事

- 不改 Pi 本身的 skill 机制，只在 psyclaw 的扩展层处理。
- 不在核心里内置新的统计算法（沿用 analysis-plan 的边界）。
- 不照搬有版权的规范原文（JARS 表格），只做改写，并给出出处链接。

## 7. 开发与审核流程

- **开发智能体**：按 A、B 的顺序分批实现，建议先 A2、A3（方法细则拆分 + 代码注入），再 B1–B5。每批一个本地提交，提交说明写清对应的开发项编号。不推送。
- **每批交审时附上**：
  - 改动的文件列表和对应的开发项；
  - `pnpm typecheck` 和相关 vitest 的输出；
  - 新增或修改的测试；
  - 已知限制、没做的部分。
- **Claude 审核内容**：
  - 是否符合第 3 节和本次定下的冲突规则（核心不可覆盖、主题冲突默认用户、同名提醒）；
  - 改动是否最小，有无顺手修改无关代码；
  - 注入总量上限、去重和 observation mask 是否配合正确，有无 token 明显上涨；
  - 无头和交互两条路径是否都有测试；
  - 安全：用户 skill 正文注入是否只来自已启用的根目录，不会绕过 data-access 规则。
- 已知的无关失败：当前 `tests/unit` 下有 10 个既有失败（skills-registry、mode 提示、help），不是本工作引入的；如果本工作改到这些文件，需要说明。
