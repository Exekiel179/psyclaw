# 多智能体开发与运行框架

本文件区分两种“多智能体”：开发 psyclaw 的工程协作面，以及 psyclaw 面向研究者执行任务的产品运行面。两者共享结构化任务、边界、验收和审计原则，但不能混为一个隐式聊天群。

## 1. 开发协作面：Orca supervised DAG

### 角色

| 角色 | 责任 | 不负责 |
|---|---|---|
| Coordinator / root | 维护目标、拆 DAG、整合结果、维护契约和用户决策点 | 不替 worker 猜测领域实现，不跳过评测 |
| Pi adapter worker | Pi API/版本适配、session/resource/extension contract | 不写领域 gates |
| Domain contract worker | Evidence/Claim/Provenance/Memory/Gate schema 与纯函数 | 不接入真实网络或模型 |
| Workflow worker | checkpoint、resume、planner/scheduler/verifier | 不并行写共享目录 |
| Integration worker | MCP/Skill/Plugin trust、manifest、依赖与许可证扫描 | 不默认启用第三方能力 |
| Eval/security worker | fixtures、契约测、对抗测试、威胁模型 | 不为通过测试放宽规则 |
| Panel worker | 事件投影、TUI widget、后续 panel contract | 不把 UI 作为事实源 |

受当前资源限制，默认每波为 root + 2 个 worker；独立任务才并行，依赖链深度不超过 3。角色不是永久组织结构，完成一个里程碑后按任务重新组合。

### TaskSpec 必填字段

```yaml
id: M1-evidence-ledger
objective: 实现 Evidence/Claim 纯数据契约和 append-only store
scope: src/research/evidence.ts, tests/unit/evidence.test.ts
out_of_scope: 网络检索、UI、统计计算
inputs: docs/架构蓝图.md
outputs: schema + tests + verification log
owned_paths: [src/research/evidence.ts, tests/unit/evidence.test.ts]
parallel_safe: true
completion:
  - npm test -- evidence
  - no raw-data write
  - all schema cases pass
```

每个 worker 必须在独立 worktree 或只读共享 worktree 中工作，禁止两个 worker 同写同一文件。Coordinator 亲自复跑验证后才接受结果；未通过的结果不合并、不用“先留着”。

### Worker report contract

每个受控 worker 只发送一次结构化报告；正文可读但不能代替字段：

```json
{
  "schemaVersion": "psyclaw/worker-report/v1",
  "taskId": "<task>",
  "dispatchId": "<dispatch>",
  "outcome": "succeeded|failed|blocked",
  "summary": "<what changed or was inspected>",
  "findings": [{"severity": "P0|P1|P2", "path": "<path>", "section": "<section>", "message": "<fact>"}],
  "filesModified": [],
  "verification": [{"command": "<exact command>", "exitCode": 0, "outputDigest": "<sha256>"}],
  "blockers": [],
  "nextOwner": "<task-or-human>"
}
```

`verification.outputDigest` 指向脱敏后的完整输出归档；没有命令输出的只读审查必须明确写 `verification: []`，不能写“已验证”。Coordinator 只接受 task/dispatch ID 与当前 Run 匹配、schema 合法且 outcome 明确的报告。

### 开发波次

```text
Wave 0  纪要/架构/威胁模型/评测案例
   |
Wave 1  [Pi adapter] || [domain contracts] || [eval fixtures]
   |
Wave 2  [project bootstrap + gates] -> [research-brief workflow]
   |
Wave 3  [read-only orchestration] || [MCP/Skill trust]
   |
Wave 4  [literature/analysis/writing packs] || [TUI/RPC projection]
   |
Wave 5  independent review -> release candidate -> human acceptance
```

Wave 1 可并行；Wave 2 依赖合同；Wave 3 只有在 M2 离线评测全绿后才开始。任何 worker 发现许可证、密钥、数据泄露或 API 不确定性，立即标记 `escalation`，不自行扩大范围。

### 工程完成定义

一个任务只有同时满足以下条件才算完成：

1. 代码/文档范围与 TaskSpec 一致，`git diff --check` 通过。
2. 单测、契约测和该任务的离线评测通过，并记录真实命令与输出。
3. 没有未解释的 `TODO`、自然语言完成声明或隐藏副作用。
4. Coordinator 在干净环境/临时目录复跑关键验证。
5. 至少一名未参与实现的 reviewer 检查 diff、风险和测试缺口。

## 2. 产品运行面：最小可验证编排

### 数据流

`request -> clarify -> typed Plan -> schedule -> execute -> receipt -> verify -> checkpoint -> human decision -> finish`

Planner 只输出 JSON Schema 合法的 Plan，不调用工具、不写文件、不声称已完成。Scheduler 只处理依赖、预算、并发和能力；Executor 调用 Pi 工具/Skill/MCP；Verifier 检查结构化回执、文件哈希、证据和必需产物；Finisher 只汇总已验收结果。

### 并行规则

- 首期最多 3 个 worker，硬上限 4。
- 只有 `deps` 已完成、`parallelSafe=true`、owned paths 不重叠且工具全为只读时才并行。
- 网络搜索、模型调用和解析可并行；写作、文件覆盖、导出、外部提交和记忆晋升默认串行。
- 失败最多自动纠偏一次；任何副作用已发生后，不因超时盲目重放，必须人工核对 receipt/idempotency key。
- 单次 run 共享总预算（turns、tokens、agents、duration），不能被分支放大。
- 迟到结果必须带 `runId/taskId/attemptId/specRevision`，版本不符则丢弃并记录，不覆盖新结果。

### 运行角色的最小集合

不用把 `academic-paper`、`deep-research` 等各自的 10+ agent 团队全部常驻。Conductor 按任务动态选最小角色：

- `researcher`：发现/整理来源
- `analyst`：方法或数据计划（统计委托外部工具）
- `critic`：反例、冲突、方法与伦理风险
- `writer`：只写已验收 Claim 的表达
- `verifier`：独立完整性和 provenance 检查

简单问题只用主 agent；只有存在真实独立任务且并行收益超过协调成本时才 fan-out。角色 Skill 按需加载，不把全套正文放进每个上下文。

## 3. 人工检查点

以下状态不可自动跳过：

- 研究问题、研究范式和伦理敏感性确认
- 使用外部网络/MCP/Plugin 或上传资料前
- integrity gate 失败、证据冲突、无法核验引用时
- 统计脚本实际运行前后，确认输入与输出口径
- 记忆从 `pending` 晋升为 `active`
- 论文/图表/数据对外导出或发布前

“自动继续”只适用于低风险、无副作用的内部步骤；任何自动继续都要写入事件日志并显示当前状态。

## 4. Orca 操作约定

开发任务使用 `orca orchestration run-create -> task-create -> worker-start -> check --wait`。每个 accepted `worker_done` 后，Coordinator 要么把同一 terminal 转交下一任务，要么显式 release；不能留下无人负责的 live worker。普通只读调研可以使用一般协作代理，但不得把它描述为有 Orca provenance 的实现任务。

## 5. 运行与开发的共同反模式

| 反模式 | 处理 |
|---|---|
| “模型说已完成” | 要求 receipt、artifact、hash 和 verifier 结果 |
| 并行 worker 共享写目录 | 立即暂停，改为只读或隔离 worktree/container |
| 为了通过评测降低门禁 | 拒绝，新增 fixture 或修正实现 |
| 一次加载所有 Skill | 回到最窄路由，记录加载理由和上下文成本 |
| 把摘要当全文/把题名相关当证据 | 降级 evidence level 或 FAIL |
| 把应用层 lease 当 OS sandbox | 使用独立进程/容器，并在威胁模型中标明 |
