# 关于本白皮书

本白皮书写给心理学、教育学、社会学及相关行为科学领域的研究者——包括研究生、青年教师、研究助理与课题负责人。它说明如何用 PsyClaw 0.29.14 完成一条从项目建仓、分析方案、脚本委托、交叉核验到学术写作的工作流，而不要求读者先成为程序员。

阅读本白皮书不需要系统学过 TypeScript 或命令行。我们假定你熟悉常见的社会科学研究设计与统计概念（如相关、回归、组间比较、信度、效应量），日常可能使用 SPSS、JASP、Excel、RStudio 或 Python，但不想把「写代码」变成研究的主业。PsyClaw 的价值不在于替你点选分析菜单，而在于：把目标、方案、脚本、结果、证据和人审决定放进可检查的项目结构里，让六个月后的你、合作者和审稿人仍能回到同一条轨迹。

请把 PsyClaw 当作一位能力很强、执行很快、但需要明确指令与严格监督的研究助理，而不是可以替代 PI 判断的黑箱。统计数字由成熟外部库或受信任的 MCP 计算；PsyClaw 负责组织过程、保存脚本与环境信息、推动核对，并在关键节点要求人审。模型会犯错，而且常常错得很有信心——本白皮书因此把「AI 产出必须验证」写成使用前提，而不是可选建议。

### 如何使用本白皮书

第一章与第二章：认识产品、安装登录、完成第一次对话。第一次使用前请完整阅读。

第三章：项目目录与三种模式（对话 / 分析 / 学术）。搭建项目时必读。

第四章：斜杠命令全解。日常翻查；做分析与定稿前尤其要读 `/plan`、`/crosscheck`、`/ars`。

第五章：四条可照做的端到端工作流。按你的任务类型选一条跟做。

第六章与第七章：Panel、人审、证据、安全与伦理。正式研究务必阅读。

第八章：排错与不应作出的承诺。出问题或对外介绍产品时查阅。

附录：命令速查、提示词模板、目录约定，供日常翻用。

文中用普通段落写出风险提示与实践建议，不依赖彩色信息框。示例中的「你可以说」可直接改写后粘贴进 PsyClaw。

# 执行摘要

核心主张：社会科学研究的数据分析与写作，正在从「点选软件 + 聊天粘贴」转向「对话式、可复现、可审计的研究工作流」。PsyClaw 让研究者用自然语言指挥项目推进，同时把脚本、结果、核验清单和交接记录留在本地项目里——可复现、可审查、可在换数据后重跑。

PsyClaw 与普通网页聊天机器人的本质区别在于：它不只回答问题，而是在你的研究项目目录里工作——读取约定路径下的材料、起草并委托分析脚本、记录核对状态、把分析交接给写作模式。你的角色从「操作软件的人」变为「指挥并审核助理的人」。正确的心智模型是：你是 PI，它是研究助理。

全流程概览（对应后续章节）：

1. 建仓与摸底：`/init` 搭好目录与 `psyclaw.md`；原始数据进入 `data/raw/` 后视为只读。
2. 澄清与方案：Shift+Tab 进入 analysis；用 `/plan` 或自然语言形成方案，回复「可以」确认，或显式 `/plan confirm`。
3. 委托与复现：统计计算在本地成熟库或特殊后端 MCP 中完成；脚本落在 `analysis/scripts/`，结果落在 `analysis/results/`。绝不让模型凭空编数字。
4. AI 核查与人审：分析前后由 AI 执行 `/crosscheck`（别名 `/verify`）把字段标为 `ai-checked`；人必须在 Panel 点「核实」或执行 `/crosscheck <id> human`。跳过（skip）不能通过门禁。
5. 交接与写作：`/plan handoff` 写入 `analysis/HANDOFF.md` 后切到 academic；文献与初稿可走 soft-route 或 `/ars`；定稿前再次 AI 核查 + 人审。
6. 压力测试与评审：`/brainstorm`、`/grill` 在定方案前加压；`/review` 做多角色模拟评审但不自动改稿。

一句话边界：通过门禁只表示通过当前合同检查，不表示结论真实、因果成立或论文可发表。正式研究仍需要研究者复核、方法学审查和适用的伦理程序。

# 第一章　认识 PsyClaw

## 1.1 PsyClaw 是什么

PsyClaw 0.29.14 是面向社会科学的研究智能体。它把研究目标、项目目录、分析方案、可复现脚本委托、交叉核验清单、人工核实、分析交接与学术写作组织进同一套本地工作流。它运行在锁定版本的官方运行时之上，但对外产品身份只有一个：**PsyClaw**。请不要把它称作其他编程助手产品名，也不要把它当成「会聊天的 SPSS」。

PsyClaw 擅长的是过程编排与可审计留痕：澄清问题、提出方案、请你确认、写出可复跑脚本的结构、推动核对、把分析产物交接给写作。它不在核心里实现统计学算法。描述统计、推断检验、建模与作图应委托成熟的 Python/R 库，或 SPSS、Stata、Mplus、受信任的 MCP；每次结果都应能回到输入、脚本、环境和证据来源。

## 1.2 为什么研究者值得用它

第一，可复现性需要脚本，而不是只靠菜单记忆。半年后要加一个协变量时，点选流程很难精确重来；脚本化分析改一行、重跑一次即可。PsyClaw 把「写脚本」的门槛降到对话，但并不取消「脚本必须可审」的要求。

第二，它把最耗时的机械劳动结构化：清理规则披露、方案确认、结果与表文对照、引文字段核验、交接清单。你的时间应花在设计、解释与伦理判断上。

第三，它强制区分「模型说做完了」与「人审通过了」。analysis 交接与 academic 定稿前，AI 核查不够，必须有人在 Panel「核实」或 `/crosscheck <id> human`。

注意：PsyClaw 不能替代统计训练与科学判断。它会生成流畅但错误的论证，会漏报效应量，会在证据不足时听起来很完整。本白皮书后续章节把验证步骤写成默认工作流。

## 1.3 正确的心智模型：你是 PI，它是研究助理

与 PsyClaw 协作的最佳心智模型，是把它当作刚入组的高能力研究助理：执行快、不怕重复劳动、能按规范落盘；但不了解你的隐性约定、偶尔过度自信、需要清晰指令与例行检查。由此推出四条原则：

1. 指令要像给 RA 布置任务一样具体。「分析一下数据」是坏指令；「用独立样本 t 检验比较两组抑郁得分，报告效应量与 95% CI，脚本写入 analysis/scripts/」是好指令。
2. 背景写进 `psyclaw.md`。研究设计、变量含义、缺失编码、报告规范写清楚后，每次会话少解释一遍。
3. 关键节点亲自把关。尤其是：原始数据不可改、方法确认、主结果数字、引文与因果表述、导出/投稿意图。
4. 发现走偏立即叫停。纠正方向，把反复出现的规则追加进 `psyclaw.md`。

## 1.4 产品边界一览

| 它做什么 | 它不做什么 |
|---|---|
| 初始化研究工作区与状态目录 | 在核心内重写统计算法或编造数值 |
| 组织分析方案、脚本路径与交接 | 把 DOI 元数据当成全文方法/结果证据 |
| AI 交叉核验 + 强制人审门禁 | 用 skip 或「AI 已核」冒充人审通过 |
| 学术模式写作、评审与导出意图 | 绕过付费墙、读取凭据、覆盖 `data/raw/` |
| 发现 Skill / MCP / Plugin | 默认自动执行未预检的外部能力 |

# 第二章　安装、登录与第一次对话

## 2.1 环境要求

需要 Node.js `>=22.19.0`。在终端运行：

```bash
node --version
```

版本号应显示 22.19.0 或更高。PsyClaw 支持 macOS、Windows 与 Linux。统计计算本身还需要你本机或 MCP 侧具备相应引擎（如 Python/R）；不确定时，启动后直接问 PsyClaw 帮你检查，而不是先在核心里「假装算出了数字」。

## 2.2 安装

官方 npm 源：

```bash
npm install -g psyclaw@0.29.14
```

确认入口：

```bash
psyclaw --help
psyclaw
```

首次启动会引导配置模型服务。模型与凭据保存在用户侧配置目录，不要把 API Key 写进命令参数、项目文件、聊天导出或 Git 仓库。

中国大陆网络若安装缓慢，可按你机构惯用的 npm 镜像策略处理；安装完成后仍用 `psyclaw --help` 验证 PATH。

## 2.3 创建第一个项目

每项研究使用独立目录：

```bash
mkdir social-support-study
cd social-support-study
psyclaw init "社会支持与研究生心理健康的关系" --paradigm survey-observational
psyclaw
```

也可以先进入对话再初始化：

```text
/init 社会支持与研究生心理健康的关系
```

`/init` 会搭建工作区目录、根目录 `psyclaw.md` 与 `.psyclaw/` 状态目录。它只负责脚手架，不会自动替你选完方法或跑完分析。未 `/init` 时仍可对话（软门禁：警告并继续），但正式分析交接与定稿仍建议先建仓。

## 2.4 五分钟上手：第一次对话

启动后你会看到输入框。假设你已把练习数据放进 `data/raw/`（真实被试数据请先完成伦理与去标识要求），可以说：

```text
请先不要修改任何文件，只做三件事：
1. 描述 data/raw/ 里这份数据的规模与变量名猜测；
2. 指出异常或缺失模式；
3. 列出澄清研究问题前还缺什么信息。
不要编造统计结果。
```

权限与确认：当系统弹出「唤醒选项」或核对清单时，优先在弹窗中选择；也可以输入编号、选项名或自然语言。回应会被记录，不应被丢弃。

快捷键：

- `Shift+Tab`：在 chat → analysis → academic 间循环切换模式。
- `Ctrl+Shift+T`：调整思考深度（多数终端比 Ctrl+Shift+Tab 更可靠）。

续接会话：

```bash
psyclaw --continue
# 或
psyclaw -c
```

# 第三章　项目结构与三种模式

## 3.1 标准目录（研究者视角）

`/init` 之后，请按生命周期放置材料。智能体不应把论文或脚本散落在项目根目录。

```text
my-study/
├── psyclaw.md                 # 项目「入组手册」：背景、码本要点、规范
├── data/
│   ├── raw/                   # 原始数据：只读圣域，永不改写
│   └── clean/                 # 经确认的派生/清洗数据
├── analysis/
│   ├── scripts/               # 可复现分析脚本（Python/R 等）
│   ├── configs/               # 方案、变量字典、参数快照
│   ├── results/               # 数值结果、表、机器可读摘要
│   ├── outputs/               # 分析侧交付物
│   ├── plans/                 # 分析方案记录
│   └── HANDOFF.md             # analysis → academic 交接
├── literature/pdfs/           # 合法取得并核验的全文 PDF
├── paper/                     # 论文 Markdown 与导出意图产物
├── notes/                     # 研究笔记与人工决策说明
├── outputs/figures/           # 对用户交付的图（常含 PNG + 可编辑 SVG）
└── .psyclaw/                  # 状态、证据、核对清单、运行与审计记录
```

最重要的一条规则：`data/raw/` 只读。清理、重编码、量表合成一律通过脚本写入 `data/clean/`，并保留输入关系。无论中间出什么错，你永远能从原始数据重来。

## 3.2 三种模式（Shift+Tab）

| 模式 | 定位 | 典型工作 |
|---|---|---|
| chat | 普通对话 | 资料整理、一般问答、轻量协作；不强制研究流水线 |
| analysis | 数据分析控制面 | 澄清 → 方案 → 脚本 → AI `/crosscheck` → 人审 → 报告 → handoff |
| academic | 学术写作控制面 | 文献、初稿、格式、评审；定稿前 AI `/crosscheck` + 人审 |

analysis 模式优先级：先产出可运行的分析结果，再做人审门禁；在宣称分析完成或写入最终交接前，必须通过人审核实。academic 模式应消费 `analysis/HANDOFF.md` 与 `analysis/results/`，不要在写作模式里重选主统计方法；缺数字时切回 analysis。

捆绑的学术研究技能（文献、写作、评审流水线等）已随 npm 包提供，日常用自然语言 soft-route 即可，不必再要求安装。非捆绑能力通过 `/skill`、`/mcp`、`/plugin` 发现；默认是「发现但不执行」，启用前需信任预检。

## 3.3 `psyclaw.md` 写什么

建议至少包含：研究概述与范式、数据说明与缺失编码、分析与报告规范（效应量、区间、探索/确证区分）、铁律（raw 只读、不编造数字、不绕过访问控制）、当前进度与遗留问题。每当你纠正了助理的反复错误，就说一句「把这条规则写进 psyclaw.md」。

# 第四章　斜杠命令全解

本章按用户主路径展开。每个命令给出用途、典型用法与注意事项。`/model` 与 `/handoff` 为开发命令，仅在章末简要说明。

### 4.1 `/init`

**用途**
搭建干净研究工作区：约定目录、`psyclaw.md` 与 `.psyclaw/` 状态目录。可带研究目标与范式信息。

**典型用法**
```text
/init 睡眠质量与大学生学业倦怠的关系
```

命令行等价示例：

```bash
psyclaw init "睡眠质量与大学生学业倦怠的关系" --paradigm survey-observational
```

**注意事项**
`/init` 只脚手架，不自动完成澄清与分析。未初始化也可继续对话，但 analysis 交接与 academic 定稿仍强烈建议先建仓。不要把敏感凭据写进 `psyclaw.md`。

### 4.2 `/plan`（及子命令）

**用途**
管理分析方案生命周期：创建、查看、确认、自动/人工审批模式、审查、执行、推迟、交接、拒绝。也可在 analysis 模式用自然语言触发 soft takeover；对方案回复「可以」常可代替显式 confirm。

**典型用法**
```text
/plan new 社交支持是否与心理健康相关，以及哪些变量可能解释这种关系
/plan status
/plan list
/plan confirm 独立样本t检验比较高低支持组抑郁得分
/plan review
/plan run
/plan defer
/plan handoff
/plan reject 设计与数据不匹配，需先改操作化
/plan auto
/plan human
```

自然语言确认示例：当方案处于待确认状态时，直接回复：

```text
可以
```

**注意事项**
- 子命令完整集合：`new` | `status` | `list` | `confirm` | `auto` | `human` | `review` | `run` | `defer` | `handoff` | `reject`。
- `/plan auto` 可跳过逐项方法人工确认，但由此产生的结果必须明确标注「未经人审批」。这不等于分析完成后的人审核验门禁。
- `/plan handoff` 在写入 `analysis/HANDOFF.md` 前会检查人审硬门禁：仅有 `ai-checked` 或 `skipped` 不能通过。
- 默认倾向本地可复现脚本；特殊后端（如 SPSS/Mplus 等）或你明确要求时再用 MCP。
- 永远不要让模型发明数值结果。

### 4.3 `/crosscheck`

**用途**
管理交叉核验清单：由 AI 核查字段并标记 `ai-checked`；由人完成真正的核实。支持按 kind 组织核验域。

**典型用法**
```text
/crosscheck list
/crosscheck kind citations
/crosscheck kind stats
/crosscheck <id> verified
/crosscheck <id> ai-checked
/crosscheck <id> human
/crosscheck <id> flagged 表与正文不一致
/crosscheck skip
```

常用 kind：`citations` | `format` | `requirements` | `stats`（以及 general 类项）。

**注意事项**
- `/crosscheck <id> verified` 由 AI 执行时会记为 `ai-checked`，**不等于**人审通过；只有 Panel「核实」或 `/crosscheck <id> human` 才会写入真正的 `verified`。
- analysis 交接（`/plan handoff`）与 academic 定稿前，硬门禁只认人审 `verified`；`ai-checked` 与 `skipped` 都不能过关。
- `/crosscheck skip` 不会解除硬门禁；跳过项不能当作完成证据。
- 清单项应来自真实核查需要；没有核查内容时不要假装全部通过。

### 4.4 `/verify`

**用途**
`/crosscheck` 的别名，行为相同：AI 核查 + 人审门禁。

**典型用法**
```text
/verify list
/verify <id> human
```

**注意事项**
对外教学与文档中可与 `/crosscheck` 互换；团队内建议统一用一个，避免两套说法。人审规则完全相同。

### 4.5 `/brainstorm`

**用途**
显式启动研究方向头脑风暴与问题澄清：提出若干有理论意义、可回答的方向，比较价值、可行性与边界，并推荐一个；按需逐题澄清。

**典型用法**
```text
/brainstorm 青少年社交媒体使用与睡眠
```

**注意事项**
头脑风暴阶段不要直接要求「写完整论文」或「给出最终 p 值」。完成后若要加压，再用 `/grill`。它帮助选题与澄清，不替代伦理审查与预注册决策。

### 4.6 `/grill`

**用途**
对研究问题、设计、方法与论证做逐题压力测试（学术追问），暴露薄弱假设、混淆与过度声称。

**典型用法**
```text
/grill 当前中介模型是否有反向因果与测量混淆风险
```

**注意事项**
`/grill` 产出的是质疑与修订建议，默认不自动改稿；是否写回项目文档需你确认。适合在定分析方案前使用，而不是在已经「编完数字」后补丁式辩解。

### 4.7 `/review`

**用途**
并发运行多角色模拟同行评审，收集结构化意见；不自动改稿。

**典型用法**
```text
/review
```

**注意事项**
通常需要已 `/init` 的项目。评审意见不是真实期刊审稿，也不能代替方法学顾问。一次只跑一个多智能体评审任务；已有任务在跑时会提示冲突。把意见当作检查清单，由你决定改哪些。

### 4.8 `/loop`

**用途**
按计划有界推进当前研究阶段；可用停止请求中断持续推进。

**典型用法**
```text
/loop
/loop stop
```

**注意事项**
有界推进不等于无限自动科研。长循环费 token，也不保证质量。需要停止时及时 `/loop stop`。它不能用来绕过人审门禁或 raw 只读规则。

### 4.9 `/panel`

**用途**
打开本地科研工作台：项目文件只读浏览、能力状态、核对清单、人审「核实」、配置与成本等视图。

**典型用法**
```text
/panel
```

**注意事项**
Panel 绑定本机本地地址，不把项目变成新的远程聊天会话。人审的主路径之一就是在 Panel 对清单项点「核实」。应用层界面不是操作系统沙箱；敏感数据仍需更强隔离策略。

### 4.10 `/help`

**用途**
打开 Panel「使用速览」页；Panel 不可用时回退为终端文字说明。

**典型用法**
```text
/help
```

**注意事项**
`/help` 是速览，不是本白皮书全文。命令变更以当前版本速览与本文件为准。可与 `/panel` 配合使用。

### 4.11 `/skill`

**用途**
查看、启用、停用或安装技能。捆绑的研究工作流技能已在包装内，日常不必再装；可选推荐技能（如文献蒸馏类）可按需发现。

**典型用法**
```text
/skill
/skill status
```

**注意事项**
默认发现不等于可执行。启用前检查来源、版本/ref、哈希、许可与依赖。不要把「安装技能」误当成分析完成。捆绑学术能力优先用模式 soft-route，而不是反复走安装对话。

### 4.12 `/skill:<name>`

**用途**
显式调用已启用的指定技能。

**典型用法**
```text
/skill:analysis-plan
```

**注意事项**
仅在需要明确点名时使用。academic 模式下非白名单技能通常需要显式 `/skill:<name>`。调用不存在或未启用的技能应失败可见，不要假装已执行。

### 4.13 `/agents`

**用途**
浏览或运行内置 / 项目级协作智能体（Subagent），执行有界任务。

**典型用法**
```text
/agents
/agents --agent <id> 请只检查方法与结果表述是否一致
```

**注意事项**
子代理适合并行分工与互查，不适合无边界「整篇代写并直接定稿」。提升权限类效果在创建与每次运行时都需要确认。结果仍要进入你的证据与人审流程。

### 4.14 `/ars`

**用途**
学术模式入口与 ARS 流程管理：查看状态、诊断、启动、完整流程、停止。

**典型用法**
```text
/ars status
/ars doctor
/ars start
/ars full <简明任务描述>
/ars stop
```

**注意事项**
`/ars doctor` 用于检查学术模式入口是否就绪，不要把它理解成「论文已经正确」。完整流程耗时与 token 成本较高，启动前确认范围。academic 模式中许多写作任务也可自然语言 soft-route；`/ars` 是显式控制面。定稿仍要 AI `/crosscheck` + 人审。

### 4.15 `/mcp`

**用途**
打开 MCP 服务器的发现与配置管理。用于连接特殊统计或数据后端等外部工具服务。

**典型用法**
```text
/mcp
```

**注意事项**
默认发现但不执行。启用前做信任预检。统计计算即便经 MCP，也必须留下可复现脚本或等价运行记录；不要在聊天里手抄「最终数字」却无法回溯。环境变量只应进入对应子进程，不在日志中回显密钥。

### 4.16 `/plugin`

**用途**
浏览推荐并管理 Plugin / Extension。

**典型用法**
```text
/plugin
```

**注意事项**
扩展会扩大能力面与风险面。来源不清、许可不明、依赖不完整的插件不要启用。捆绑研究工作流不要求再通过 `/plugin install` 安装。

### 4.17 `/provider`

**用途**
查看、配置或切换模型服务提供方。

**典型用法**
```text
/provider
/provider <provider-id>
```

**注意事项**
换模型不会自动重算已通过人审的结果；只改变后续生成行为。凭据仍按本地认证配置管理，不要写进项目。模型服务异常时先查 Provider 与网络，再查具体 Skill/MCP。

### 4.18 `/export`

**用途**
使用内置能力导出会话或相关交付意图（例如将会话内容导出备查）。论文 DOCX 等学术导出应在有稿件与人审之后按写作流程提出，而不是用导出代替核验。

**典型用法**
```text
/export
```

**注意事项**
导出会话不等于论文定稿。若在尚无 `paper/` 稿件时要求 Word，应明确那是分析报告导出，不要标注为已完成论文。正式投稿前仍须完成引文与人审门禁。

### 4.19 `/pet`

**用途**
管理启动横幅宠物显示：开启、关闭或查看状态。

**典型用法**
```text
/pet status
/pet on
/pet off
```

**注意事项**
纯界面偏好，不影响分析正确性、门禁或安全策略。

### 4.20 `/create-skill`

**用途**
预览并创建项目级技能；需确认后落盘。

**典型用法**
```text
/create-skill
```

按提示提供标识与说明，先预览再确认。

**注意事项**
项目级技能仍受信任与权限约束。不要创建「自动跳过人审」或「允许改 raw」类技能。先小范围验证，再在团队复用。

### 4.21 `/create-hook`

**用途**
创建分析生命周期 Hook（声明式），用于在特定分析阶段附加检查或提示。

**典型用法**
```text
/create-hook
```

**注意事项**
Hook 是辅助治理，不是绕过 Verifier 的后门。错误的 Hook 可能造成噪音或误阻断；变更应可审计。

### 4.22 `/create-rule`

**用途**
创建项目级附加规则，补充 `psyclaw.md` 之外的约束。

**典型用法**
```text
/create-rule
```

**注意事项**
规则应可执行、可理解，避免与伦理底线冲突。不要把未验证的「期刊潜规则」写成强制事实。

### 4.23 `/create-subagent`

**用途**
创建项目级协作智能体定义，供 `/agents` 有界调用。

**典型用法**
```text
/create-subagent
```

**注意事项**
创建与运行若涉及提升效果，需要再次确认。子代理输出同样不能代替人审与证据门禁。

### 4.24 开发命令（非主路径）

`/model`：列出或切换模型；需启用开发命令。普通用户优先用 `/provider` 与首次配置流程。

`/handoff`：写入机器可读交接检查点；需启用开发命令。用户主路径的分析交接请用 `/plan handoff` 生成 `analysis/HANDOFF.md`，不要把开发用 `/handoff` 当作日常步骤。

# 第五章　可复现工作流

以下四条流程可按编号照做。示例主题可替换；不可替换的是：raw 只读、不编造数字、AI 核查后必须人审、skip 不通过门禁。

## 5.1 问卷调查分析：从建仓到学术交接

目标：完成一份可复现的问卷分析，并合法交接给写作模式。

1. 建目录并安装确认后进入项目：

```bash
mkdir sleep-burnout-study && cd sleep-burnout-study
npm install -g psyclaw@0.29.14   # 若尚未安装
psyclaw
```

2. 用户输入：

```text
/init 睡眠质量与大学生学业倦怠的关系
```

期望产出：出现 `data/`、`analysis/`、`paper/`、`psyclaw.md`、`.psyclaw/` 等约定结构。

3. 将去标识后的练习数据放入 `data/raw/`（不要改文件内容）。用户输入：

```text
Shift+Tab
```

切到 analysis。然后输入：

```text
数据在 data/raw/。请先摸底：变量、缺失、反题项线索。
提出可回答的研究问题与分析方案选项，不要编造结果。
```

期望产出：数据概况、澄清问题、可选方案；可能出现唤醒选项供你选择。

4. 用户输入：

```text
/plan new 睡眠质量与学业倦怠的相关及回归，控制年级与性别
```

或对推荐方案直接回复：

```text
可以
```

期望产出：活跃 Plan；状态可 `/plan status` 查看。

5. 用户输入：

```text
/plan run
```

期望产出：在 `analysis/scripts/` 生成/更新可复现脚本，委托成熟库计算；`analysis/results/` 出现结果摘要或表图路径。若缺 Python/R，系统应说明需要什么，而不是假装算完。

6. 用户输入：

```text
请对样本量、主效应、效应量与区间、表文一致性做交叉核验。
/crosscheck kind stats
/crosscheck list
```

期望产出：相关项变为 AI 已核（`ai-checked`）。此时仍不可宣称分析完成。

7. 打开工作台并人审：

```text
/panel
```

在核对清单上对关键项点「核实」；或：

```text
/crosscheck n human
/crosscheck primary-effect human
```

期望产出：对应项为人审通过；skip 的项仍不能算通过。

8. 用户输入：

```text
/plan handoff
```

期望产出：写入 `analysis/HANDOFF.md`（目标、完成项、限制、下一步）。若人审未过，应被拦截并提示。

9. `Shift+Tab` 到 academic，用户输入：

```text
请阅读 analysis/HANDOFF.md 与 analysis/results/，起草结果部分提纲。
不要重新选择主分析方法；缺数字就指出缺口。
```

期望产出：基于已有结果的写作提纲或 `paper/` 草稿起点，而不是新编统计。

## 5.2 文献综述与初稿：academic + ARS + 评审

目标：在已有分析交接或明确文献任务时，推进综述与初稿，并用模拟评审找漏洞。

1. 进入已建仓项目，`Shift+Tab` 到 academic。

2. 用户输入：

```text
/ars doctor
```

期望产出：学术模式入口诊断信息；按提示处理缺失项。

3. 用户输入：

```text
/ars start
```

或直接自然语言 soft-route：

```text
请基于我给出的研究问题做有界文献梳理：构念定义、主要理论、方法分歧与冲突证据。
只使用可核验来源；不确定就标记 uncertain，不要编造文献。
```

期望产出：结构化文献笔记或研究简报草稿；冲突证据并列，而不是只留有利方向。

4. 若需要完整流程且你已确认范围与成本：

```text
/ars full 社交支持与研究生抑郁：综述并形成引言草稿骨架
```

期望产出：分阶段产物；长任务应可 `/ars stop` 中止。

5. 写作时用户输入：

```text
把已核验材料写入 paper/intro-draft.md。
凡依赖文献的陈述必须可回溯；不要为了凑引用堆无关文献。
```

期望产出：`paper/` 下 Markdown 初稿。

6. 用户输入：

```text
/review
```

期望产出：多角色模拟评审意见；不自动改稿。你挑选必改项后，再要求修订。

7. 定稿前不要跳过第六章核验流程（见 5.4）。

## 5.3 压力测试研究方案：先 `/grill` 或 `/brainstorm`，再定分析

目标：在动数据之前暴露设计风险，减少「先跑完再找理由」。

1. `/init` 后保持 chat 或 analysis。用户输入：

```text
/brainstorm 短期干预能否改善考试焦虑
```

期望产出：2–4 个可回答方向、利弊比较与推荐；逐题澄清而非直接写论文。

2. 选定方向后用户输入：

```text
/grill 该准实验的选择偏倚、依从性与多重结局风险
```

期望产出：尖锐问题清单与文档更新建议；你确认哪些写回 `psyclaw.md` 或预注册笔记。

3. 进入 analysis，用户输入：

```text
根据刚才压力测试后的边界，提出主分析与敏感性分析方案。
探索性与确证性分开。然后 /plan new
```

期望产出：带边界披露的 Plan，而不是忽略 `/grill` 结论硬上因果表述。

4. 再按 5.1 从 confirm/run → crosscheck → 人审 → handoff 推进。

## 5.4 定稿前核验：引文交叉核验 → 人审 → 导出意图

目标：在宣称全文完成或准备导出 Word 之前，走完硬门禁。

1. academic 模式下用户输入：

```text
请对正文关键主张与参考文献做交叉核验，重点检查 DOI 与字段一致性。
/crosscheck kind citations
```

期望产出：引文相关清单项进入 AI 已核；无法核验的条目被标记，而不是静默保留。

2. 用户输入：

```text
/crosscheck list
```

核对仍为 unverified / flagged / skipped 的项。

3. 用户输入：

```text
/panel
```

对必须通过的项点「核实」；或：

```text
/crosscheck citations human
```

期望产出：人审通过记录。注意：只有 AI 已核不能定稿。

4. 用户输入（示例）：

```text
在人审通过的前提下，将 paper/ 中的稿件按 APA 7 导出意图准备 DOCX。
若仍有未核验引文或未下载全文，列出阻塞项，不要宣称可投稿。
```

期望产出：导出准备或明确阻塞列表；会话 `/export` 不能替代这一步的人审。

5. 若分析数字在写作中发现缺失，切回 analysis 补算，而不是在 academic 模式编造。

# 第六章　Panel、人审与交叉核验

## 6.1 Panel 是什么

`/panel` 打开本机科研工作台，用于查看项目文件投影、能力状态、核对清单，并完成人审「核实」。它让门禁可见，而不是只靠模型口头说「已经核对」。

## 6.2 AI 核查与人审的分工

| 动作 | 谁做 | 状态含义 | 能否过交接/定稿门禁 |
|---|---|---|---|
| `/crosscheck` 字段核查 | AI | `ai-checked` | 否 |
| Panel「核实」或 `/crosscheck <id> human` | 人 | 人审通过（verified） | 是（在门禁要求范围内） |
| `/crosscheck skip` | 人/流程 | `skipped` | 否 |

analysis 完成与 academic 定稿前：先 AI `/crosscheck`（别名 `/verify`），再强制人审。软警告可用于中期草稿；最终化是硬门禁。

## 6.3 唤醒选项与选择记录

当需要在多个方案中选择、确认下一步或勾选清单时，系统应通过唤醒选项提供结构化选择：单选 `mode=choice`，多选/清单 `mode=checklist`。你也可以输入编号、名称或自由文本；系统应规范化并记录原文、最终选项、上下文、时间与来源。没有模型实际发起核验时，不要假设清单已自动填满。

## 6.4 推荐人审节奏

- 分析前：研究问题/estimand、方法选择、缺失与排除规则。
- 分析后：N、主效应与不确定性、表文一致、方法与脚本一致、关键主张不过度因果。
- 写作定稿：引文 DOI/字段、格式与投稿要求相关项。

# 第七章　证据、安全与伦理底线

## 7.1 证据原则

- DOI 或题录只能证明文献可能存在，不能自动证明方法、结果或因果结论。
- 具体数值必须来自真实分析产物，不能由模型补写。
- 冲突证据必须并列披露，不能只保留有利方向。
- 探索性与确证性分析分开表述；自动模式结果须披露「未经人审批」。
- 质性研究不因缺少效应量而被判无效，但应保留编码轨迹、反身性与反例。
- 没有定位、来源或必要产物时，使用 `uncertain` 或阻断，而不是写得更流畅。

## 7.2 数据与隐私

原始/敏感资料未经授权不得进入外部模型或网络。先去标识、最小化字段，再分析。`data/raw/`、凭据、`.git` 与符号链接逃逸目标不可写。机构订阅全文应走合法访问，不绕过付费墙、验证码或账号墙。

## 7.3 Skill、MCP、Plugin 信任

默认发现但不执行。启用前核验来源、版本/ref、哈希、许可、依赖与信任状态。副作用需要结构化 receipt、审批记录与幂等键；Verifier 不接受「模型说完成了」作为完成证据。

## 7.4 伦理与署名

涉及人的研究遵守你所在机构的伦理审查与知情同意要求。AI 辅助应在适用的披露规范下说明。PsyClaw 可以降低执行成本，但不能代你承担作者责任。

## 7.5 安全边界的诚实表述

应用层门禁不是操作系统级沙箱。高敏感数据、高风险插件与不可逆发布，仍需要更强隔离与制度审批。

# 第八章　排错与不应作出的承诺

## 8.1 常见排错

| 现象 | 先做什么 |
|---|---|
| 找不到 `psyclaw` 命令 | `node --version`；重开终端；检查 npm 全局 PATH |
| 模型无法调用 | `/provider`；网络；凭据是否误写入项目 |
| 学术模式异常 | `/ars doctor`；再 `/ars status` |
| 看不到核对清单 | 确认是否已发起 `/crosscheck`；打开 `/panel` |
| `/plan handoff` 失败 | 检查人审是否完成；`skip`/`ai-checked` 不够 |
| 统计跑不起来 | 检查本机 Python/R 或 MCP；读脚本错误日志；禁止手填假数字 |
| 会话中断 | `psyclaw --continue` 或 `psyclaw -c` |
| 需要总览 | `/help` 或本白皮书第四章 |

## 8.2 不应作出的承诺

不要向合作者、学生或审稿人承诺以下内容：

1. 「已经通过 PsyClaw 门禁」= 结论真实或因果成立。
2. 「AI 核查过了」= 可以定稿或投稿。
3. 「有 DOI」= 该文支持你的具体统计句。
4. 「模型写完了脚本」= 数字正确。
5. 「模拟 `/review` 通过」= 期刊会接收。
6. 「安装了 MCP/Skill」= 已获得正确推断。
7. PsyClaw 替代 IRB/伦理审查、数据治理或作者署名规范。

通过门禁只表示通过当前产品合同检查。正式研究仍需要研究者复核、方法学审查和适用的伦理程序。

# 附录 B　可复制提示词模板

**摸底（只读）**

```text
请先不要修改任何文件。描述 data/raw/ 中数据的规模、变量与异常，列出分析前必须澄清的问题。不要编造统计结果。
```

**形成方案**

```text
基于已澄清的研究问题，提出主分析与 1–2 个敏感性分析，区分探索/确证，说明输入、假设、输出与限制。用唤醒选项让我选择。
```

**确认执行**

```text
可以。请把确认的方法写入方案，在 analysis/scripts/ 生成可复现脚本并运行；结果写入 analysis/results/。不要发明数字。
```

**分析后核验**

```text
请对 N、主效应、效应量与置信区间、表文一致性、方法与脚本一致性做 /crosscheck。完成后停下，等人审，不要宣称已完成交接。
```

**人审提醒（给自己）**

```text
打开 /panel，对清单关键项点「核实」，或使用 /crosscheck <id> human。不要用 skip 凑通过。
```

**交接写作**

```text
请在人审通过后执行 /plan handoff，并基于 analysis/HANDOFF.md 起草 paper/ 结果与方法提纲。禁止重选主分析或补造统计量。
```

**压力测试**

```text
/grill 请追问测量效度、混淆、多重比较与因果表述风险；每轮一个实质问题，并给出你建议的边界披露。
```

**定稿前引文**

```text
/crosscheck kind citations
请列出无法双源核验或缺少本地全文的条目；在人审完成前不要宣称可导出投稿。
```

# 附录 C　项目目录约定

| 路径 | 约定 |
|---|---|
| `data/raw/` | 原始资料只读；禁止覆盖、删除、重编码 |
| `data/clean/` | 研究者确认后的派生数据 |
| `analysis/scripts/` | 可复现脚本；不要把脚本丢在仓库根目录 |
| `analysis/configs/` | 方案、码本、参数与预注册快照 |
| `analysis/results/` | 数值结果与机器可读摘要 |
| `analysis/outputs/` | 分析侧输出 |
| `analysis/plans/` | Plan 记录 |
| `analysis/HANDOFF.md` | analysis → academic 交接真源之一 |
| `literature/pdfs/` | 合法取得并验证的全文 |
| `paper/` | 论文 Markdown 与导出产物 |
| `notes/` | 笔记、人工决策说明 |
| `outputs/figures/` | 交付图；常需 PNG + 可编辑 SVG |
| `psyclaw.md` | 项目说明书（每次会话应遵循） |
| `.psyclaw/` | 状态、证据账本、核对清单、运行与审计；非对外文稿目录 |
